# 設計メモ

## 全体の流れ

```
[主催者]                     [参加者]                  [Google]
   |                            |                          |
   | 1. /new で候補を作る        |                          |
   |--- 空き時間を問い合わせ ------------------------------->| freeBusy
   |<-- 予定の入っていない枠 -------------------------------|
   |                            |                          |
   | 2. 調整ページの URL を共有 ->|                          |
   |                            | 3. ○△× を入力            |
   |<-- 集計 --------------------|                          |
   |                            |                          |
   | 4. 日時を確定               |                          |
   |--- 予定を作成（Meet 付き）--------------------------->| events.insert
   |<-- Meet の URL ---------------------------------------|
   |                            |                          |
   | 5. 確定文面を共有 --------->|                          |
```

## 技術選定と、その理由

| 選んだもの | 理由 | 捨てた選択肢 |
|---|---|---|
| **Next.js（App Router）** | 1つのリポジトリで画面とAPIが完結する。Vercel などにそのまま載る | 画面とAPIを分けるSPA構成（デプロイ先が2つ増える） |
| **Server Actions** | フォーム送信に JavaScript を必須にしない。参加者側が軽い | クライアントからの fetch + API ルート |
| **`node:sqlite`（Node 22 標準）** | 依存パッケージが増えない。ローカルで即動く | Prisma（生成物とエンジンの管理が増える） |
| **`fetch` で Google API を直叩き** | `googleapis` は数十MB。使うのは4つのエンドポイントだけ | `googleapis` パッケージ |
| **Tailwind CSS v4** | 設定ファイルなしで動く | 独自CSS（分量が増える） |

### `node:sqlite` を選んだことの弱点

**Node 22 では experimental 扱い**で、将来 API が変わる可能性があります。
また **SQLite はファイルなので、Vercel のようなサーバーレス環境では永続しません**。
本番運用するなら Postgres 等への差し替えが必要です。

差し替えやすいよう、**SQL は `src/lib/db.ts` と `src/lib/repo.ts` の中だけ**に閉じ込めてあります。
画面もアクションも SQL を知りません。

## 権限（スコープ）の考え方

要求している Google の権限は2つだけです。

- `calendar.events` — 確定した予定を**作る**ため
- `calendar.freebusy` — **空き / 予定あり**の時間帯だけを読むため

`calendar.readonly` を要求すれば予定のタイトルや参加者まで読めますが、
日程調整には不要なので**あえて要求していません**。
freeBusy が返すのは「この時間は埋まっている」という区間だけで、**予定の中身は取得しません**。

## セキュリティ上の割り切り

| 対象 | 方式 | 割り切りの中身 |
|---|---|---|
| 調整ページ | 推測しにくい10文字のID | **URL を知っていれば誰でも見られます**（調整さんと同じ） |
| 主催者ページ | 32バイトの秘密トークン | URL に含まれるので、共有時に取り違えないよう画面で警告 |
| 回答の編集 | 参加者ごとの秘密トークン | 他人の回答は書き換えられません |
| OAuth | `state` を cookie と突き合わせ | CSRF 対策。戻り先は自サイト内パスのみ許可 |
| セッション | httpOnly cookie + DB照合 | 30日で失効 |

**やっていないこと**：レート制限、監査ログ、暗号化保存、招待制。
社外に公開して不特定多数に使わせる想定なら、これらの追加が要ります。

## 集計ロジック

`○ = 2点 / △ = 1点 / × = 0点` の合計で並べ替え、同点なら○の数、さらに同点なら開始が早い順。

**「×が1つでもあれば除外」という強い規則は入れていません。**
キーパーソンの○を優先したい、といった事情は機械には見えないためです。
順位付けはあくまで**提案**で、決めるのは主催者です。

## ファイル構成

```
src/
  app/
    page.tsx                  トップ（作成した調整の一覧）
    new/page.tsx              作成画面
    p/[id]/page.tsx           投票・確定内容の閲覧（参加者向け）
    p/[id]/manage/page.tsx    集計・確定・通知（主催者向け）
    setup/page.tsx            Google 連携の設定手順
    actions.ts                Server Actions（作成・回答・確定・通知）
    api/
      auth/google/start       OAuth 開始
      auth/google/callback    OAuth コールバック
      auth/logout             ログアウト
      suggest                 空き時間からの候補提案
  components/
    PollForm.tsx              作成フォーム
    VoteForm.tsx              ○△× 入力
    ResultTable.tsx           集計表
    ShareBar.tsx              共有ボタン群
  lib/
    db.ts / repo.ts           SQLite とデータ操作
    google.ts                 OAuth・freeBusy・events
    time.ts                   タイムゾーン計算と候補生成
    share.ts                  文面と各サービスの共有リンク
    notify/line.ts            LINE Messaging API への push
    notify/webhook.ts         Slack / Discord 等への POST
```

## これから足すとしたら（優先順）

1. **参加者側のカレンダー連携** — 参加者も Google と繋いで、○△× を自動で埋める
2. **回答の締め切りとリマインド** — 未回答者へ自動で催促
3. **Postgres 対応** — サーバーレスにそのまま載せるため
4. **1対1の予約受付モード** — Google の予約スケジュールに相当する使い方
5. **LINE 公式アカウントの Webhook 受信** — トークから直接調整を開始する
